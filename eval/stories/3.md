## The defect

Two shelf commands started in the same moment (two processes on the same `shelf.json`) both wrote
and renamed the one temporary file `.shelf.json.tmp`. The first rename installed whatever that file
held last, which could be the other process's document; the second rename found no temporary file
and reported `cannot write shelf.json (ENOENT)`, exit 1. So the command that reported failure had
its change on disk and the command that reported success had none. That breaks the PRD's
Failed-command definition (section 4: a failed command never changes the file).

## What to build

Name the temporary file for the writing process, so two commands at once never write to or rename
each other's temporary file (TD-20). The blueprint fixes the name as `.shelf.json.<pid>.tmp`, with
the process id read from `node:process` as an import (the store's lint rule bars the `process`
global; an import from a `node:` module is allowed). Everything else about the write stays: the
writability check first, the whole document written to that file, the rename over `shelf.json`, and
on any failure that file removed and `unwritable` thrown.

What the reader then sees (REQ-08 c5): a command refused because the file cannot be written changes
nothing, so its book keeps its status in `list`; a command that exits 0 printed a line that was true
of the shelf at some moment, so at least one exit-0 command's change shows in `list` afterwards. One
of two successful changes may still be lost: no lock, last write wins (blueprint section 8, TD-17)
stands and is not yours to change.

directory after a successful or a refused write.
