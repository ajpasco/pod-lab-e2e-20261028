# D-3: A reader that closes the pipe early makes `list` print Node's unhandled EPIPE stack

- Seen: With a long shelf (20,000 books, about 1.4 MB of `list` output), `node app/shelf.mjs list | head -1` prints the first line (`1 to read Book number 1`) and `node` exits 1 (bash `PIPESTATUS[0]`), with 14 lines on stderr beginning `node:events:497`, `throw er; // Unhandled 'error' event`, the `Error: write EPIPE` stack. `node app/shelf.mjs list | true` does the same (23 stderr lines). With stdout destroyed after the first chunk, `node` exits 1 and stderr begins `node:events:497`. `shelf.json` is untouched. Cause, read in `app/shelf.mjs`: the boundary writes the whole output with `process.stdout.write` and installs no handler for a write error on stdout, so Node's default (an unhandled `error` event, a stack, exit 1) applies; blueprint section 12 recorded "Output write failure (stdout closed): excluded, not handled beyond Node's default" as a recorded default.
- Requires: none: the PRD is silent on a reader that closes the pipe. Blueprint section 12, "Output write failure (stdout closed)", excluded it as a recorded default; the founder's decision below replaces that default.
- Behaviour to decide: the PRD is silent. Defensible: a silent exit 0 when stdout closes early (the reader asked for less and got it); one error line and exit 1; exit 141 as a shell would report SIGPIPE. The founder's choice, in their words (2026-10-28, ajpasco): "fix now, the boundary in app/shelf.mjs, stderr empty and exit 0 when stdout closes early".
