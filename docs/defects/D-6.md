# D-6: A symbolic link named `shelf.json` is replaced by a regular file on the first write, and the link's target never changes

- Seen: Two directories, `synced/` holding `shelf.json` as {1 to read Dune} and `here/` holding `shelf.json` as a symbolic link to that file. In `here/`, `node app/shelf.mjs list` prints `1 to read Dune` and exits 0 (the link is followed on read). `node app/shelf.mjs done 1` prints `done 1 Dune` and exits 0, but afterwards `here/shelf.json` is a regular file, no longer a link, holding book 1 as `read`, while `synced/shelf.json` is byte-for-byte unchanged (`1 to read Dune`); `list` in `synced/` still shows `1 to read Dune`. The change the command reported never reached the file the reader linked to, and every later command in `here/` works on the new regular file, so the two copies drift apart silently. Cause, read in `app/src/store.mjs`: the write method of blueprint section 7 writes `.shelf.json.<pid>.tmp` and renames it over the path `shelf.json`; `rename` replaces the link itself, not the file it points to.
- Requires: none: the PRD is silent on links. PRD section 2 says the shelf is `shelf.json` in the current directory; REQ-03 c1 says `done 1` prints `done 1 Dune`, exits 0, and `list` then shows `1 read Dune`, which holds in `here/`. Blueprint section 7's write method (TD-8, accepted by the user, Q18 item 1, D4) is what replaces the link; nothing in the blueprint speaks of a linked `shelf.json`.
- Behaviour to decide: the PRD is silent. Defensible: (a) follow the link and write its target (resolve the real path before the temporary file and rename, so the rename replaces the target in its own directory); (b) refuse a linked `shelf.json` as unwritable (exit 1, a message, nothing changed); (c) record it as an accepted limitation. Recommended, if it is fixed: (a). The founder deferred it (below), so no behaviour is chosen yet.
