# D-2: Two shelf commands run at once: the one that reports success loses its change, and the one that reports failure is what gets written

- Seen: With `shelf.json` holding {1 to read Dune; 2 to read Emma}, start `done 1` and `done 2` at the same moment (two processes). In the orchestrator's ten trials, 3 came out inverted: `done 1` exited 1 with `shelf: cannot write shelf.json (ENOENT)` on stderr and nothing on stdout, `done 2` exited 0 and printed `done 2 Emma`, and `shelf.json` afterwards had book 1 `read` and book 2 `to read`: the failed command's change is on disk and the successful command's is not. 2 more trials had both exit 0 with one change lost (the lost update blueprint section 8 accepts); 5 were clean. The tester saw 6 inverted of 10 for `done`, and for `add A` with `add B` in an empty directory 4 of 10 where `add A` printed `added 1 A` and exited 0 while `add B` exited 1 and the file held exactly one book, `B`, as book 1. Cause, read in `app/src/store.mjs`: both processes write the same `.shelf.json.tmp`; the first rename installs whatever that file held last (the other process's document), and the second rename finds no temporary file (ENOENT) and reports unwritable.
- Requires: PRD section 4, Failed command ("a failed command never creates or changes it, and leaves the disk as it was" [Q13]); REQ-08 c4 ("In each case nothing is changed on disk") for the command refused with the cannot-write message; REQ-01 c1 and REQ-03 c1 in that the printed line (`added 1 A`, `done 2 Emma`) must describe what was stored. Blueprint section 8 and TD-17 accept "last write wins; an earlier concurrent change can be lost" and note "Two writers share the temporary file's name; that is not guarded", but describe neither a failed command writing the file nor a successful one writing nothing.
- Behaviour to decide: the PRD is silent on two commands at once, though its Failed-command definition already says a non-zero exit changes nothing. Defensible: (a) accept and record it: amend blueprint section 8 to say what really happens (when two commands overlap, the exit code and the printed line can both be wrong about what is on disk); (b) give each process its own temporary file name (for example `.shelf.json.<pid>.tmp`), so each rename installs the document of the process that reports success: the lost update of TD-17 stays (both exit 0, the last writer wins), but a non-zero exit never changes the disk and a printed line always describes a document that was on disk; (c) a lock on `shelf.json`, which section 8 declined. Recommended: (b); it keeps the recorded default, restores the Failed-command definition, and changes one constant and one line in the store. The founder's choice, in their words (2026-10-28, ajpasco): "fix now, option (b), a per-process temporary file name". It enters the PRD as REQ-08 criterion 5 (amendment 2) and the blueprint as TD-20 (section 14, delta 2).
