# D-5: A command killed while it writes leaves a stray `.shelf.json.<pid>.tmp` file beside the shelf for good

- Seen: Stage `shelf.json` as {1 to read Dune} followed by 1000 to-read books with 40,000-character titles (about 40 MB, so the write takes long enough to be interrupted). Start `node app/shelf.mjs done 1` and send it `SIGTERM` (or `SIGINT`) the moment its temporary file `.shelf.json.<pid>.tmp` appears. The process ends by the signal (exit null, signal SIGTERM, or 143 from a shell's `wait`; stdout and stderr empty), `shelf.json` is byte-for-byte the staged document (the old file stays whole, as blueprint section 12 promises), `list` afterwards exits 0 and shows `1 to read Dune`, but the directory now holds `.shelf.json.<pid>.tmp` beside `shelf.json`. Six of six trials for the tester (SIGTERM ×3, SIGINT ×3) and six of six for the orchestrator. A later successful `done 1` in the same directory (exit 0, `done 1 Dune`) does not remove it: the store removes only the file named for its own process, so the stray stays until the reader deletes it by hand, and each interrupted write adds another. Cause, read in `app/src/store.mjs`: `writeShelf` removes the temporary file only in its `catch`; a signal ends the process between `writeFileSync(TEMP_FILE)` and `renameSync`, and nothing runs after that.
- Requires: none: the PRD is silent. The Failed-command definition (PRD section 4) speaks of a non-zero exit code, which a killed process has none of; blueprint section 7 ("if any step fails, remove that temporary file and report unwritable") covers a failing step, not a signal; blueprint section 12, Shutdown ("A kill mid-write leaves the old file whole (temporary and rename)"), says what happens to `shelf.json`, which holds, and nothing about the temporary file. The rows T-REQ-01-N6 and T-REQ-08-N1 to N3 assert no temporary file after a successful or a refused write, not after a kill.
- Behaviour to decide: the PRD is silent. Defensible: (a) accept it and record it in blueprint section 12's Shutdown line ("…and may leave `.shelf.json.<pid>.tmp` behind, which the reader may delete"); the file is hidden, nothing is lost, and the trigger is the reader killing the command inside a window of milliseconds. (b) On the next successful write, remove stale `.shelf.json.<p>.tmp` siblings whose process `p` no longer exists (`process.kill(p, 0)` throwing `ESRCH`), never a live writer's, so TD-20 stands. (c) Install `SIGINT` and `SIGTERM` listeners in the boundary; because the write is synchronous, the listener cannot run until the write and rename are done, so a kill during the write lets the millisecond-long command finish whole and exit normally, leaving no temporary file (`kill -KILL` would still leave one). Recommended: (a), defer; if the founder wants it fixed, (c) is the smallest change. The founder deferred it and chose (a)'s record, not a behaviour (below): the Shutdown line records the stray file, and no behaviour is chosen yet.
- Row: T-REQ-08-N5 (`eval/tests/defects.test.mjs`; listed in `eval/deferred.txt` as `T-REQ-08-N5 D-5`, so the runner reports it apart from the verdict; a `done 1` on the 40 MB shelf above is sent SIGTERM the moment its temporary file appears, then a later `done 1` must exit 0 and print `done 1 Dune`, which it does only if the kill left the shelf whole with the book on it, and the directory must then hold exactly `shelf.json`; it fails against main `6ba654d` because `.shelf.json.<pid>.tmp` is still there after the later write; it passes whether a fix lets the interrupted command finish whole (option c) or sweeps the stray on the next successful write (option b), and under option (a) it stays deferred, so it chooses none of the three; eval plan section 12, delta 4)
